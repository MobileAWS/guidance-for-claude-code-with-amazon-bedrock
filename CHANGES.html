Fork Changes Audit

Every change in this repo that differs from upstream aws-solutions-library-samples, with the reason it was made and a verified verdict on whether it's actually needed — calling out what's redundant with AWS-native controls, obsolete after the Go port, or solvable with a simpler pattern.

Scope & method

  • In scope: the deployment-kit changes that stay in this repo — the credential helper, the OTel helper/collector, package.py + install scripts, and the auth/monitoring CloudFormation.
  • Out of scope (per request): the Nexus management API and console platform (nexus-* lambdas + infra) — those move to allcode-nexus-ui in Phase 3, so auditing them here is moot. They are referenced where a kit-side feature depends on them.
  • Method: each verdict is checked against the actual code/templates (file references given), not asserted. The guiding question throughout: could this be done with native AWS config/IAM, or is it redundant with something upstream already provides?
Several fork features are being ported to Go in Phase 2 (device flow, platform reporting, model enforcement, sidecar). This audit judges the feature, not the language — a "redundant" verdict means the feature should arguably be dropped, not merely re-implemented.

Runtime auth & telemetry

1 · Client-side model enforcement REDUNDANT

What
The credential helper reads enabled_models from the quota response and rewrites ~/.claude/settings.json so ANTHROPIC_MODEL is one of the admin-allowed models (config.EnforceEnabledModels / Python _enforce_enabled_models).
Justification
To stop users from using models the admin hasn't approved.
Verified
Enforcement is already done by IAM. The federated role's BedrockAccessPolicy scopes bedrock:InvokeModel by resource ARN (bedrock-auth-cognito-pool.yaml:97-107; default is foundation-model/*, narrowed to the enabled set). A user who picks a disallowed model gets an IAM AccessDenied regardless of settings.json. The client rewrite provides no security — a user can re-edit their own settings file and IAM still blocks them — so it's purely UX (avoids the error by auto-switching).
Verdict
Could be done purely in AWS IAM, and is. The model allowlist belongs in the role policy (one place, tamper-proof). The client rewrite is a redundant convenience layer at the wrong altitude.
Recommend
Drop client-side enforcement. Keep the IAM allowlist as the single control. If the "no confusing AccessDenied" UX matters, surface it once at install/auth time (a printed note of allowed models) rather than silently rewriting a user-owned file on every credential refresh.

2 · Local OTel collector sidecar SIMPLIFY

What
Claude Code exports OTLP to localhost:4318, where a per-machine otelcol daemon (auto-started by ensure_collector_running) batches and SigV4-exports straight to CloudWatch. Ships sidecar-config.yaml, a custom-built otelcol, and the 7.9 MB ocb builder binary committed to git.
Justification
"Reliable token counting" / OTel latency fix — local batching + retry, and SigV4 via the machine's <profile>-collector credentials so export doesn't depend on JWT TTL.
Verified
Upstream needs no local sidecar: Claude Code exports OTLP directly to a central ECS/Fargate collector behind an ALB that JWT-validates (otel-collector.yaml:158-252), and otelHeadersHelper injects the bearer + attribution headers. The fork's sidecar instead pushes the SigV4→CloudWatch step onto every client (sidecar-config.yaml exporter), which removes the central collector but adds: a daemon, PID/auto-start management, per-user CloudWatch PutMetricData IAM, and a platform-specific compiled binary to distribute.
Verdict
A legitimate trade (drop the Fargate cost) but a heavyweight one. The reliability gain (retry buffer) is real; the cost is significant client complexity and a build artifact in the repo. Upstream's direct-to-ALB path is materially simpler and already battle-tested.
Recommend
Re-evaluate against upstream's direct model. If the central collector cost is the only driver, weigh it against the per-machine operational burden. At minimum, never commit ocb (build it in CI) and don't auto-spawn a daemon from a credential/telemetry helper if the direct OTLP path meets the SLA.

3 · Platform reporting (/api/users/platform) REDUNDANT

What
After auth, the credential helper POSTs {email, platform, arch} to the Nexus hub (best-effort).
Justification
Inventory of which OS/arch each user runs, for the management console.
Verified
The kit already emits per-user attributed telemetry through OTel (email, user id, org, dept, etc. — otel/extract.go). OS/arch is trivially addable to that existing stream. A second bespoke POST to a hardcoded hub endpoint duplicates a channel that already exists and carries the same identity.
Verdict
Low-value duplication. It also re-introduces a hardcoded hub URL on the auth hot path (the device-flow caveat applies).
Recommend
Drop the dedicated POST; if platform inventory is wanted, add os.type/os.arch as OTel resource attributes (one line in the extractor) and read them in the console from the data you already collect.

4 · Device-code flow NEEDED (conditional)

What
Portless OAuth device-code auth: the CLI gets a code from the Nexus hub, the user approves in a browser, the CLI polls for tokens. Used when device_auth_endpoint/quota_api_endpoint is set.
Justification
Lets the Nexus hub broker auth centrally (multi-tenant), and works where a local redirect server can't bind (locked-down/headless machines).
Verified
This is genuinely distinct from upstream's browser-redirect OIDC — it has no local equivalent. It's justified for the multi-tenant hub model. For a single-org deployment authenticating straight to Cognito/Okta, upstream's browser OIDC already works and device flow adds a hub dependency.
Verdict
Keep where the hub brokers auth; it's not redundant. But it's only necessary for the centralized multi-tenant story — single-tenant installs don't need it.
Recommend
Keep, but make the hub base URL config-driven (still falls back to a hardcoded default today — see nexus.DefaultAPIBase). Externalize before any public push.

5 · Application-inference-profile ARN overrides SIMPLIFY

What
Optional inference_profile_{opus,sonnet,haiku}_arn profile fields that override ANTHROPIC_*_MODEL / ANTHROPIC_MODEL in the generated settings with Application Inference Profile ARNs (config.py:107, package.py settings writer).
Justification
Native AWS cost allocation — Application Inference Profiles carry cost-allocation tags so spend shows up per-team in Cost Explorer.
Verified
Upstream already resolves models per-tier via cross_region_profile (CRIS) and attributes cost via session tags (showTags/getTag, the Project/CostCenter principal tag → OTel x-project). That's a second, overlapping cost-attribution mechanism.
Verdict
Not strictly redundant (inference profiles tag at the Bedrock-invocation layer; session tags attribute in telemetry) — but maintaining both cost-attribution paths is complexity. One is likely enough.
Recommend
Pick one cost-attribution mechanism. If Cost Explorer allocation is the goal, standardize on inference profiles and drop the session-tag path (or vice-versa). Don't ship both half-wired.

6 · CLAUDE_CODE_DISABLE_THINKING=1 VERIFY / likely stale

What
Generated settings disable extended thinking.
Justification
A historical 400 error — some Bedrock models rejected the thinking message format.
Verified
This was a point-in-time model-compatibility workaround (per KEY_FIXES.md). Current Bedrock Claude models support extended thinking.
Verdict
Likely stale — and it degrades the product (thinking off by default) to dodge a bug that's probably gone.
Recommend
Test against current models; if the 400 is gone, remove it so users get thinking by default.

Packaging & install

7 · Auto-install prerequisites (Python 3 + AWS CLI) SIMPLIFY

What
install.sh auto-installs Python 3 (via brew/apt/yum/dnf) and the AWS CLI if missing.
Justification
Smoother onboarding — don't make users hand-install dependencies.
Verified
AWS CLI is not required at runtime — upstream's own installer says so ("the credential process binary handles authentication directly") and the Go binaries are self-contained. Python 3 is only needed by the install script itself to parse config.json.
Verdict
The AWS-CLI auto-install is unnecessary. The Python 3 auto-install is a means to an end (script-time JSON parsing) that pulls a system-package install with sudo — heavy for what it does.
Recommend
Drop AWS-CLI auto-install. Avoid the Python dependency in the installer entirely — the credential-process Go binary can emit the parsed config (or accept a --print-config helper), removing the need to sudo apt install python3 at install time.

8 · CodeBuild-Windows build path OBSOLETE after Go

What
Windows binaries are built asynchronously in AWS CodeBuild (has_codebuild_windows, nexus/CodeBuild plumbing, console URL helpers in package.py).
Justification
PyInstaller can't cross-compile; building Windows binaries required a Windows runner.
Verified
The Go binaries cross-compile to Windows from any host — verified in Phase 2 (GOOS=windows builds both credential-process and otel-helper cleanly). Once the build is Go-only, the entire CodeBuild-for-Windows apparatus has nothing to do.
Verdict
Obsolete the moment Phase 2b flips the build to Go. It's pure carrying cost (a whole async build path, status polling, console-URL formatting) for a problem Go doesn't have.
Recommend
Remove with the PyInstaller path in Phase 2b. This is one of the largest simplifications available.

9 · .aws/credentials stale-stanza purge (Windows) NEEDED

What
install.bat purges any leftover [profile] stanza from %USERPROFILE%\.aws\credentials before writing config.
Justification
A stale stanza there (e.g. an EXPIRED placeholder) is resolved by the AWS credential chain before credential_process in config, shadowing it and breaking Cowork Desktop with a 403 InvalidClientTokenId.
Verified
This is a real, specific failure mode of the AWS credential-resolution order, not something IAM or config alone fixes — the two files genuinely conflict.
Verdict
Justified bug fix. Keep.
Recommend
Keep, but consider upstreaming it — it's a generic correctness fix, not Nexus-specific. (Confirm the macOS/Linux installer has the equivalent guard.)

10 · macOS code-signing & quarantine handling PARTLY REDUNDANT

What
package.py signs macOS binaries and strips the quarantine xattr (~11 references vs upstream's ~3).
Justification
Gatekeeper blocks unsigned/quarantined executables.
Verified
Upstream also signs (3 references), so the fork's signing partly duplicates upstream logic — the fork added ~8 references on top, the merge-resolution kept the fork's variant.
Verdict
The capability is needed (cross-compiled darwin binaries still need signing); the fork-specific extra is largely redundant with upstream's.
Recommend
Diff the fork's signing block against upstream's and keep only the genuine delta; let upstream own the rest so future merges stay clean.

11 · Install Claude Code.command + run.sh NEEDED (minor)

What
A macOS double-click installer wrapper and a quick-launch script that sets the profile + verifies creds.
Justification
Non-technical-user convenience (double-click install; one-command launch).
Verified
Small, self-contained, no AWS-native equivalent. Low cost, low risk.
Verdict
Fine to keep — genuinely additive UX.
Recommend
Keep. (run.sh uses python3 for config parsing — same dependency note as #7.)

Hygiene & reconciled

12 · Committed build artifacts HYGIENE

What
67 tracked artifact files differ from upstream: the 7.9 MB source/otel_helper/ocb binary (a macOS-arm64 build tool — useless on other platforms) and a large set of committed __pycache__/*.pyc bytecode.
Justification
None intended — accidental commits / a .gitignore gap.
Verified
Upstream tracks none of these. They bloat the repo, are platform-specific, and go stale.
Verdict
Remove from version control; build tools/bytecode don't belong in git.
Recommend
git rm the ocb binary and all __pycache__; add/repair .gitignore entries (__pycache__/, *.pyc, the collector build output). Build ocb/otelcol in CI.
